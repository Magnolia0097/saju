### 0.2 불변 규칙 (모든 단계 공통)

1. 금액·상품·기간은 서버가 `products` 기준으로 결정한다. 클라이언트가 보낸 금액은 쓰지 않는다.
2. 유료 본문과 근거 블록은 서버 밖으로 나가지 않는다. 클라이언트에는 티저 문장과 READY 리포트만 내려간다.
3. 모든 쓰기는 서버(service_role) 또는 security definer RPC로만 한다. 클라이언트 권한은 '본인 데이터 읽기'뿐이다.
4. READY가 된 리포트는 다시 생성하지 않는다. 스냅샷이 곧 상품이다.
5. LLM에는 이름·생년월일·출생 시각을 보내지 않는다. 8글자·피처·근거 블록만 보내고 호칭은 `{{name}}` 치환으로 처리한다.
6. 만세력·피처 로직은 `engine_version`으로 관리한다. 로직이 바뀌어도 기존 프로필·리포트는 재계산하지 않는다.
7. 새 테이블은 생성 즉시 RLS 활성화 + 클라이언트 쓰기 권한 회수 템플릿(7.2절 끝)을 적용한다.

## 1. 프로젝트 개요

- **서비스 컨셉**: 로그인 없이 대화형 입력으로 무료 사주 티저를 보여주고, **990원 건별 결제** 또는 **친구 초대 무료 티켓**으로 4,000~5,000자 심층 리포트를 여는 웹 서비스
- **벤치마크 현황 (2026-11 확인)**: 두루미는 카카오 로그인 후 '알'(코인)을 충전해 쓰는 구조다. 만세력은 직접 계산하고 풀이는 AI가 정리하며, 5개 운 점수·대운·세운 흐름까지 제공한다. 즉 'AI 풀이·다축 분석'은 차별점이 아니라 기본값이다.
- **현실적인 차별화 후보** (10장에서 결정)
  1. 코인 충전 없는 990원 건별 결제 — 사용자 마찰이 적고 PG 심사에도 유리
  2. 친구 초대 무료 티켓 루프
  3. 톤·캐릭터·공유 카드 등 브랜드 경험
  4. 특정 타깃 특화 (예: 직장인 커리어·이직 테마 강화)
- **핵심 과제**
  1. 결제 심사 통과 (유의업종)
  2. 만세력 정확도 (일주 오류 0)
  3. 리포트 품질(모순 없는 하나의 이야기) + 일관성(스냅샷)
  4. 보안 (RLS, 페이월 서버 컷)
  5. 유입 — 990원은 볼륨 게임 (4.2절)

## 2. 사용자 여정 (User Flow)

1. **랜딩**: 캐릭터 헤드라인 + `[내 사주 무료로 확인하기]`. 로그인 없음.
2. **대화형 입력 (4단계 카드)**: `1/4 성별` → `2/4 생년월일(양력/음력/윤달)` → `3/4 태어난 시간("모름" 지원)` → `4/4 닉네임`
   - 온보딩 시작 시 Turnstile 검증과 함께 **Supabase 익명 세션** 생성 (사용자는 인지하지 않음)
   - 초대 링크(`?ref=CODE`)로 들어왔다면 익명 세션 생성 직후 서버가 `pending_ref_code`를 1회 기록
   - 22:30~01:30 출생, 절입일 출생자에게는 "기준에 따라 일주·월주가 달라질 수 있어요" 안내
3. **무료 티저** (LLM 미사용, 3.7절): 일주 동물·키워드, 오행 분포 차트, 핵심 기질 3줄, 섹션별 제목 + 티저 1~2문장. 잠긴 영역은 **서버가 본문을 보내지 않고** 더미 텍스트를 블러 처리
4. **잠금 해제** — 두 경로 모두 카카오 연결 필요 (익명 세션에 `linkIdentity`로 카카오를 연결하면 같은 user_id 유지)
   - A. `[990원으로 전체 풀이 보기]` → 주문 생성 → 포트원 결제창 (토스페이·카카오페이 등)
   - B. `[친구 초대하고 무료로 보기]` → 초대 링크 발급·카카오톡 공유
   - 이미 가입된 카카오 계정이면 기존 계정으로 로그인한 뒤 익명 세션의 프로필을 병합 (6.4절 `/api/auth/merge`)
5. **리포트 생성 대기**: 20~60초 예상. "캐릭터가 풀이를 쓰는 중" 진행 화면 (스트리밍 표시 가능)
6. **리포트 열람**: 스냅샷 영구 보관. 하단에 다른 테마·궁합 추천, 공유 카드(60일주 정적 이미지) 저장·카카오톡 공유

## 3. 해석 엔진 v2 — 결정론 계산 + 근거 블록 + LLM 1회 생성

### 3.1 파이프라인

```
[입력] 성별 · 생년월일(양/음/윤) · 출생 시각(또는 모름) · 닉네임
   │
   ▼ 시간 보정 (3.3)     서머타임 해제 → 표준시 이력 → 경도 보정
   ▼ 만세력 계산 (3.3)   4주 8자, 대운(방향·대운수), 세운
   ▼ 피처 추출 (3.4)     feature_keys = 축별 조건 키 (결정론, 순수 함수)
   │
   ├─▶ [무료] 티저 조립 (3.7)   근거 블록의 teaser_text만 사용, LLM 없음
   │
   └─▶ [언락] 리포트 생성 (3.6)
          근거 블록 조회 → LLM 1회 생성(JSON) → 검증
          → 실패 시 재시도(최대 3회) → 그래도 실패하면 fallback 조립
          → reports.content_json 스냅샷 저장 (이후 불변)
```

### 3.2 왜 하이브리드인가

| 요구 | v1 (템플릿 조립) | v2 (근거 블록 + LLM 1회) |
|---|---|---|
| 일관성 (같은 입력 → 같은 결과) | 순수 함수로 보장 | 계산·피처는 순수 함수, 문장은 최초 1회 생성 후 스냅샷으로 보장 |
| 개인화 체감 | 블록 5개 나열, 축 간 모순 가능 ("내향적" vs "도화살로 사교적") | 축을 엮은 하나의 서사 + 모순 검증 |
| 콘텐츠 제작량 | 약 490블록 × 800~1,000자 | 약 190블록 × 300~600자 (근거) |
| 변동비 | 0원 | 리포트 1건당 약 30~50원 (3.6.6) — 990원의 3~5% |
| 통제 | 완전 통제 | 근거 블록 밖 해석 금지 + 금지 표현·사실 검증 |

무료 티저는 템플릿만 쓰므로 비구매자에게 드는 LLM 비용은 0원이다.

### 3.3 만세력 계산 정책

| 항목 | v2 기본값 | 비고 |
|---|---|---|
| 연주 경계 | 입춘 절입 **시각** | 1월 1일·음력 설이 아님 |
| 월주 경계 | 12절(입춘·경칩·청명·입하·망종·소서·입추·백로·한로·입동·대설·소한) 절입 시각 | 분 단위, KST |
| 월간·시간 | 오호둔(연간 → 인월 천간), 오서둔(일간 → 자시 천간) | 부록 A |
| 시간 보정 ① 표준시·서머타임 | 출생 시각을 IANA 시간대 `Asia/Seoul`로 해석해 UTC로 변환 (luxon). 1948~51·1955~60·1987~88년 서머타임과 1954~61년 UTC+8:30 표준시가 자동 반영됨 | 사전 검증: 1988-07-15 14:20 → UTC+10:00, 1960-01-15 → UTC+8:30, 1957-07-15 → UTC+9:30 확인 |
| 시간 보정 ② 경도 보정 | **보정 시각 = UTC + 8시간 30분** (기본, 표준시 대비 −30분 상당) / 옵션: UTC + 경도×4분, OFF(= UTC+9) | 서울의 실제 태양시는 표준시보다 약 30분 늦음. 설정값 `SOLAR_OFFSET` |
| 시간 보정 ③ 경계 시각 | 서머타임 전환으로 존재하지 않거나 두 번 있는 벽시계 시각은 luxon 해석 결과를 쓰고 `ambiguous` 플래그 | 결과 화면에 안내 |
| 자시 처리 | **야자시·조자시**: 보정 시각 기준 자정에 일주 변경, 23~24시는 당일 일주 + 다음 날 기준 자시 간지 | 학파 이견이 큼 → 정책 플래그 `ZI_POLICY`(`YAJASI`/`JEONGJASI`). 레퍼런스 만세력의 '야자시 적용' 결과와 대조. 경계 출생자에게 안내 + 대안 일주 표시 |
| 음력 변환 | `korean-lunar-calendar` (KASI 기준, 1000~2050년) | 실측: 1950~2049년 중 **1,348일**에서 한국·중국 음력 날짜가 다름 → 중국 기준 변환 사용 금지 |
| 절입 시각 | `astronomy-engine`으로 태양 황경(입춘 315° … 소한 285°) 도달 시각 계산 → 1900~2100년 표를 빌드 시 JSON으로 생성해 번들 포함 | 실측: `lunar-javascript`(UTC+8 기준)와 2,412건 비교 최대 1.04분 차 |
| 일진(일주) | 산술식: 60갑자 인덱스 = (율리우스일 + 49) mod 60, 0 = 갑자 | 실측: 1900~2100년 73,414일 `lunar-javascript`와 불일치 0, `korean-lunar-calendar`와도 0 |
| 시간 모름 | 3주 6자로 계산, 시주 의존 피처 제외 (가중치 재정규화) | 리포트에 정확도 안내 고정 문구. 대운수 계산은 12:00 가정 |
| 대운 | 양남음녀 순행 / 음남양녀 역행. 대운수 = 다음(역행은 이전) 절입까지 일수 ÷ 3 반올림 | 나머지 처리 방식은 학파 차이 → 설정값. 10년 단위 |
| 세운 | 입춘 기준 연도 간지 | 2026 = 병오(丙午), 2027 = 정미(丁未) |

**구현 지침**
- 만세력은 외부 API 없이 TypeScript 순수 함수 패키지(`@saju/core`)로 구현한다 (버전 `calc-x.y.z`).
- **절입 비교는 절대 시각(UTC)**, **일·시 경계는 보정 시각**으로 분리해서 계산한다.
- 런타임에서 천문 계산을 하지 않는다 (Workers CPU 제약). 절입 시각은 빌드 시 생성한 JSON 표를 조회한다.
- `lunar-javascript`는 교차검증용 개발 의존성으로만 쓴다 (중국 기준이라 음력 변환에 쓰면 안 됨).
- 예시: 1988-07-15 14:20 서울 출생 → tzdata로 UTC 04:20 (당시 서머타임 UTC+10) → +8:30 = 보정 시각 12:50 → 오시(午時). 팔자 = 戊辰 己未 辛未 甲午. 보정을 빼면 미시(未時)가 되어 시주가 바뀐다.
- 사전 검증 스크립트와 결과: `docs/research/`

**골든 테스트 (Step 1 완료 기준)**
- 300건 이상: 1950~2010년 무작위 + 경계 케이스 (절입 ±30분, 22:30~01:30, 서머타임 시작·종료일, 윤달, 1954~1961년 표준시 구간, 시간 모름)
- 기준: KASI 음양력 + 시중 만세력 2곳 이상과 대조. 불일치는 '버그' 또는 '정책 차이'로 분류해 정책 표에 기록

### 3.4 피처 추출 (feature_keys)

**공통 계산 규칙**
- 오행 개수: 천간 4 + 지지 4(지지는 오행 기준) = 8자. 시간 모름이면 6자.
- 십성: 일간 기준. 지지는 본기(정기) 천간으로 판정 (부록 A).
- 신강/신약 (v1 휴리스틱, 감수 후 조정): 일간을 돕는 글자(비겁·인성)의 가중치 합 ÷ 전체 가중치 ≥ 0.5이면 신강.
  - 가중치: 월지 3.0 · 일지 1.5 · 년지 1.0 · 시지 1.0 · 월간 1.0 · 시간 1.0 · 년간 0.8 (시간 모름이면 시주 제외 후 재계산)
- 개수 상태 (재성·배우자성): 일간 제외 7자(시간 모름이면 5자) 중 0개 = 없음, 1개 = 약, 2개 = 적정, 3개 이상 = 과다

| 축 코드 | 범위 | 조건 키 규칙 | 키 수 |
|---|---|---|---|
| `ILJU` | 공통 | 일간 + 일지 (`GAP_JA` … `GYE_HAE`) | 60 |
| `SEASON` | 공통 | 월지 (`M_JA` … `M_HAE`) — 사회적 무대·계절 환경 | 12 |
| `ELEMENT` | 공통 | 최다 오행 × 최소 오행 (`EX_WOOD__LK_METAL`). 동률이면 최다는 월지 오행 우선 → 목화토금수 순, 최소는 목화토금수 순. 최다 ≤ 2이고 최소 ≥ 1이면 `BALANCED` | 21 |
| `TENGOD` | 공통 | 주도 십성 그룹(비겁·식상·재성·관성·인성) × 신강/신약 (`SIKSANG_STRONG`). 동률이면 월지 본기의 그룹 우선 → 관성 > 재성 > 식상 > 인성 > 비겁 | 10 |
| `SHINSAL` | 공통 | **다중 라벨**. 도화·역마·화개·천을귀인·양인·괴강·백호·귀문관·원진·원국 충·원국 합 중 성립하는 것을 전부 계산하고, 우선순위(이 순서, 설정값) 상위 2개를 리포트에 사용. 없으면 `NONE` | 12 |
| `DAEUN` | 공통 | 현재 대운 천간의 십성 (`DAEUN_JEONGJAE` 등) | 10 |
| `SEUN` | YEAR | 세운 천간의 십성(10) + 세운 지지와 일지의 관계(합·충·원진·형·중립 5) | 15 |
| `WEALTH_LENS` | WEALTH | 재성 개수 상태 4 × 신강/신약 2 — '신강재약·재다신약' 관점 | 8 |
| `LOVE_LENS` | LOVE | 배우자성 상태 4 × 성별 2 (남 = 재성, 여 = 관성) + 일지(배우자궁) 12 | 20 |
| `CAREER_LENS` | CAREER | `TENGOD` 키를 재사용, 직업 관점으로 서술 | 10 |
| `PAIR` | PAIR | 일간 관계 6(비화·내가 생·나를 생·내가 극·나를 극·천간합) + 일지 관계 5 + 오행 보완 3(상호·일방·없음) | 14 |
| **합계** | | | **약 192** |

- 일지 관계 판정 우선순위: 충 > 원진 > 합(육합) > 형 > 중립 (예: 사신은 합이자 형 → '합'). 설정값으로 관리
- 오행 보완: A의 최약 오행이 B에 2개 이상 있으면 'A가 보완받음'. 양방향이면 상호, 한쪽이면 일방
- 배틀 점수(PAIR): 서버가 PAIR 키로 계산하는 결정론 점수. 예: 기본 60 + 일간 관계 ±15 + 일지 관계 ±15 + 오행 보완 최대 +10, 40~99 범위로 제한. 낮은 점수도 해설은 긍정형

  "time_known": true,
  "ILJU": "BYEONG_O",

  "TENGOD": "BIGEOP_STRONG",
  "SHINSAL": ["DOHWA", "YEOKMA", "CHUNG"],
  "SHINSAL_TOP2": ["DOHWA", "YEOKMA"],
  "DAEUN": { "current": "DAEUN_PYEONJAE", "start_age": 7, "next_change_year": 2031 },
  "WEALTH_LENS": "JAE_WEAK__STRONG",

### 3.5 근거 블록 (content_blocks)

- 블록 1개 = `teaser_text`(무료 1~2문장) + `grounding_md`(해석 포인트 bullet 300~600자) + `fallback_md`(선택, LLM 실패 대비 완성 문단)
- 공통 125개(ILJU 60 · SEASON 12 · ELEMENT 21 · TENGOD 10 · SHINSAL 12 · DAEUN 10) + 테마 렌즈 67개 = 약 192개, 근거 본문 9만 자 안팎
- 제작 파이프라인: 강한 모델로 초안 → 사람 검수(명리 원리 정합성·금지 표현·톤·중복) → `REVIEWED` → `PUBLISHED`. 수정하면 `version`을 올리고, 리포트 스냅샷에는 사용한 블록 버전을 기록
- 타 서비스·서적 문장 복제 금지 (저작권). 고유 문체 가이드 1장을 먼저 쓰고 시작
- MVP 범위를 줄인다면 공통 125개 + LIFE·YEAR 렌즈부터

### 3.6 LLM 리포트 생성 계약

**3.6.1 입력 (모델에 보내는 것)**
- `chart_facts`: 8글자(한자·한글), 오행 개수, 십성 분포, 신강/신약, 신살 목록, 현재·다음 대운, (YEAR) 세운 간지와 관계, (PAIR) 두 사람 피처와 배틀 점수
- `grounding`: 섹션별로 매칭된 근거 블록의 `grounding_md`
- `section_plan`: 3.6.3 표의 섹션 키·의도·목표 분량
- `style`: 톤, 긍정 프레이밍, 구체적 생활 예시, `{{name}}` 호칭
- `rules`: 근거 블록에 없는 신살·격국·사건 창작 금지, 금지 표현(5.6절), JSON만 출력
- **보내지 않는 것**: 실명, 생년월일, 출생 시각, 사용자 식별자

**3.6.2 출력 스키마**
```json
{
  "headline": "한 줄 요약 (40자 이내)",
  "sections": [
    { "key": "core", "title": "소제목", "body": "마크다운 본문" }
  ],
  "closing": "마무리 한 문단 (200자 이내)"
}
```
고지 문구("재미와 자기이해를 위한 해석이며 미래를 단정하지 않습니다")는 LLM이 아니라 템플릿으로 붙인다.

**3.6.3 테마별 섹션 계획 (합계 4,000~5,000자)**

| 테마 | 섹션 (사용 축 · 목표 분량) |
|---|---|
| LIFE 평생 종합 | 타고난 본성(ILJU 900) · 삶의 무대(SEASON 700) · 무기와 약점·개운법(ELEMENT 800) · 일하고 돈 버는 방식(TENGOD 800) · 사람과 매력(SHINSAL 700) · 인생 흐름과 다음 전환점(DAEUN 600) |
| YEAR 신년 운세 | 올해의 키워드(SEUN 천간 700) · 나와 올해의 궁합(SEUN 지지 × ILJU 800) · 지금 대운 위의 올해(DAEUN 700) · 일·돈 포인트(TENGOD + SEUN 800) · 사람·연애 포인트(SHINSAL 700) · 조심할 점과 개운 팁(ELEMENT 500) |
| WEALTH 재물 | 돈그릇(WEALTH_LENS 1,000) · 버는 방식(TENGOD 900) · 새는 구멍(ELEMENT 800) · 재물 타이밍(DAEUN 800) · 실천 팁(700, 투자 권유 금지) |
| LOVE 연애·결혼 | 연애 스타일(ILJU 900) · 배우자 자리(LOVE 일지 800) · 끌리는 사람 vs 독이 되는 사람(LOVE 배우자성 + SHINSAL 1,000) · 인연 타이밍(DAEUN 800) · 관계 팁(600) |
| CAREER 직업·이직 | 일하는 성향(ILJU 900) · 조직형 vs 독립형(CAREER_LENS 1,000) · 맞는 환경·직무(SEASON + ELEMENT 900) · 전환 타이밍(DAEUN 800) · 커리어 팁(500) |
| PAIR 궁합·배틀 | 첫인상 케미(일간 관계 900) · 생활 케미(일지 관계 900) · 서로 채워주는 기운(오행 보완 800) · 부딪히는 지점과 해법(900) · 배틀 점수 해설(500) |

**3.6.4 검증 (서버, 생성 직후)**
1. JSON 스키마 일치, 섹션 키·순서가 계획과 동일
2. 섹션별 분량이 목표 ±25% 이내, 전체 3,800자 이상
3. 금지 표현 정규식(5.6절) 0건
4. 사실 정합성: 일주명이 첫 섹션에 등장, '부족/과다' 오행 언급이 `ELEMENT` 키와 일치, 신강/신약 표현 일치
5. 실명·숫자 생년월일 없음, `{{name}}` 외 호칭 없음
6. 실패하면 실패 사유를 넣어 재생성 (최대 3회, `svc_claim_generation`) → 그래도 실패하면 `fallback_md` 조립 + `generation_meta.fallback = true` → 이것도 실패하면 `svc_refund_report`

**3.6.5 모델·파라미터**
- 경량 모델(Flash·Haiku·mini급)을 한국어 품질로 A/B 테스트 후 선택. 환경변수로 교체 가능하게
- temperature 0.4~0.6, 최대 출력 토큰 상한 설정, 응답은 스트리밍으로 받아 진행 화면에 표시
- `generation_meta`에 모델명·프롬프트 버전·블록 버전·입출력 토큰·원화 비용·지연시간 기록

**3.6.6 비용 추정**
- 가정: 입력 4~6천 토큰, 출력 5~8천 토큰 (한국어 4,500자 기준, 토크나이저마다 다름)
- Flash급 공시 단가 예: 입력 백만 토큰당 0.75달러(약 1,090원), 출력 3.75달러(약 5,440원) → 건당 약 0.022~0.035달러 = **약 30~50원**
- 운영 규칙: 건당 100원 초과 시 알림, 일일 LLM 비용 상한 설정

### 3.7 무료 티저 (LLM 미사용)

- 일주 동물: 천간 색(갑을 푸른 · 병정 붉은 · 무기 노란 · 경신 흰 · 임계 검은) + 지지 띠 → 예: 갑자 = 푸른 쥐, 병오 = 붉은 말
- 오행 분포 차트 (8자 또는 6자 기준 개수)
- 핵심 기질 3줄 = `ILJU` · `ELEMENT` · `TENGOD` 블록의 `teaser_text`
- 테마별 섹션 제목 + 첫 섹션 티저 1~2문장. 나머지는 잠금(더미 텍스트 블러)
- (선택) 사주 타입 배지: 결정론 점수로 산출하되 명칭은 모두 긍정형 (예: '대기만성형')

## 5. 결제·사업자·법무

### 5.1 PG 심사 현실 (포트원 자료, 2026년 9월 기준)
- 사주·운세는 여러 PG의 '유의업종'이라 조건부 개별 심사를 받는다. **KG이니시스·네이버페이(Npay)·엑심베이·키움페이는 취급 불가**
- 토스페이먼츠·KCP·나이스정보통신·스마트로·KICC·웰컴페이먼츠·카카오페이·토스페이는 입점 가능으로 분류 (빌링·포인트 충전형은 제약 가능)
- 카카오페이 등 간편결제사는 PG와 별도로 자체 심사를 하며, 제한 업종은 더 까다로울 수 있다
- 심사에 유리한 구조 = v2 구조: 건별 즉시결제, 입력값 기반 자동 생성 리포트형(상담형 아님), 결제 직후 제공, '확정적 미래 예측' 표현 제거
- 한 PG에서 거절돼도 다른 PG에 신청할 수 있으므로 처음부터 2~3곳 동시 신청
- 정책은 수시로 바뀌므로 신청 시점에 포트원 헬프센터·각 PG 기준을 재확인

### 5.2 준비 서류

### 6.5 결제 → 생성 시퀀스
1. 서버: `orders` 생성 (PENDING, 금액은 `products.price_krw`)
2. 클라이언트: 포트원 결제창 호출 (paymentId = order_id, 금액 = 서버가 준 값)
3. 결제창 복귀 → `/api/payments/complete` → 포트원 단건 조회 (상태 PAID, 금액 일치 확인)
4. `svc_mark_order_paid` 결과별 처리
   - `OK` → `reports` 행(GENERATING) 생성됨 → 생성 페이지로 이동
   - `AMOUNT_MISMATCH_CANCEL_REQUIRED` / `ALREADY_UNLOCKED_CANCEL_REQUIRED` → 즉시 포트원 취소 → 주문 상태 반영
5. 웹훅이 먼저 오든 나중에 오든 같은 함수가 멱등 처리
6. 생성 페이지: `/api/reports/:id/generate` 호출 → 진행 화면 → READY면 렌더
7. 이탈 대비: 리포트 페이지 재방문 시 GENERATING이고 잠금이 만료됐으면 재호출 (최대 3회)

## 7. 데이터베이스 스키마 (Supabase DDL v2)

### 7.1 설계 요지
- `app_users`는 `auth.users`와 1:1 (가입 트리거로 자동 생성) → RLS에서 `auth.uid()`를 그대로 사용
- 익명 사용자도 `authenticated` 역할 → 프로필·티저는 가능, 티켓·결제는 RPC에서 카카오 연결 여부로 차단
- 티켓은 원장(`ticket_ledger`) 합계로만 계산하고, 차감은 사용자 행을 잠근 뒤 원자적으로 처리
- `reports` 유니크 인덱스: `LEAST/GREATEST(profile_id, partner_profile_id)` × 테마 × 기간 (환불 건 제외) → 1인·2인(순서 무관)·연도별 상품을 한 규칙으로 처리
- `orders`는 탈퇴해도 결제 기록 보존 (`on delete set null`)
- `content_blocks`는 정책 없음 + 권한 회수 → 서버(service_role)만 읽음
- 서버 전용 함수는 `svc_` 접두사, `service_role`에만 실행 권한

### 7.2 DDL

원본: `supabase/migrations/20261109000000_init.sql` — 검증 완료, **수정 금지** (변경은 새 타임스탬프 마이그레이션으로)

| 객체 | 종류 | 요지 |
|---|---|---|
| `app_users` | 테이블 | `auth.users`와 1:1, 내 초대 코드, 유입 초대 코드(`pending_ref_code`) |
| `private.handle_new_user` | 트리거 함수 | 가입(익명 포함) 시 `app_users` 자동 생성 |

| `reports` | 테이블 | 언락·생성 상태·스냅샷, 순서 무관 유니크 인덱스 |

**오류·결과 코드 (앱에서 분기 처리)**
- `rpc_unlock_with_ticket` 예외: `AUTH_REQUIRED` · `KAKAO_LOGIN_REQUIRED` · `INVALID_PRODUCT` · `INVALID_PERIOD` · `PAIR_MISMATCH` · `PROFILE_NOT_OWNED` · `PARTNER_NOT_OWNED` · `NO_TICKET` · `ALREADY_UNLOCKED`
- `svc_mark_order_paid` 결과: `OK` · `ORDER_NOT_FOUND` · `ORDER_NOT_PENDING` · `AMOUNT_MISMATCH_CANCEL_REQUIRED` · `ALREADY_UNLOCKED_CANCEL_REQUIRED`
- `svc_confirm_referral` 결과: `REWARDED` · `HELD`(`RISK_REVIEW`) · `REJECTED`(`LIFETIME_CAP` · `DAILY_CAP`) · `NO_REFERRAL` · `REFEREE_NOT_LINKED` · `EXPIRED` · `NO_SELF_PROFILE` · `ALREADY_PROCESSED` · `INVALID_REFERRER`
- `svc_refund_report` 결과: `TICKET_RESTORED` · `ORDER_REFUNDED` · `ALREADY_REFUNDED` · `NOT_FOUND`

**새 테이블 추가 템플릿**
```sql
alter table public.<new_table> enable row level security;
revoke insert, update, delete, truncate on public.<new_table> from anon, authenticated;
create policy <new_table>_select_own on public.<new_table>
  for select to authenticated using (user_id = (select auth.uid()));
```

### 7.3 검증 결과 (2026-11-09, 로컬 PostgreSQL 16)
Supabase 권한 모델(anon / authenticated / service_role 역할, public 스키마 기본 권한 전체 부여, `auth.uid()`)을 흉내 낸 환경에서 위 DDL을 실행하고 아래를 확인했다.

| 구분 | 테스트 | 결과 |
|---|---|---|
| 권한 | 비로그인: 상품 조회 가능, 프로필 0건, 해석 원문 접근 거부, 티켓 RPC 실행 거부 | 통과 |
| 권한 | 로그인 사용자: 본인 프로필만 조회, 원문 접근 거부, 원장 직접 INSERT · app_users UPDATE · reports UPDATE · TRUNCATE 거부, 서버 전용 함수 실행 거부 | 통과 |
| 트리거 | 비슈퍼유저 인증 역할로 auth.users INSERT → app_users 자동 생성 | 통과 |
| 티켓 | 잔액 없음 → `NO_TICKET`, 남의 프로필 → `PROFILE_NOT_OWNED`, 익명 → `KAKAO_LOGIN_REQUIRED`, 기간·쌍 불일치 거부 | 통과 |

| 동시성 | 잔액 1장에서 두 세션 동시 언락 → 1건 성공 · 1건 `NO_TICKET`, 최종 잔액 0 | 통과 |
| 결제 | 금액 위변조 → FAILED 기록 + 취소 요청, 정상 결제 → 리포트 생성, 재호출 멱등, 이미 언락된 대상 결제 → 취소 요청 | 통과 |
| 생성 | 점유 중 재점유 불가, 3회 초과 점유 불가 | 통과 |
| 환불 | 티켓 리포트 환불 → 티켓 복구, 중복 환불 거부, 환불 후 재언락 가능 | 통과 |

## 8. 친구 초대 & 어뷰징 방어 v2

### 8.1 보상 규칙
- 초대자: 카카오 연결된 회원. 피초대자 1명이 확정되면 무료 티켓 +1
- 피초대자 인정 조건 (모두 충족)
  1. 초대 링크로 유입된 **새 세션**에서 시작 (`pending_ref_code` 기록, 7일 유효)
  2. 그 세션이 **새 카카오 계정으로 연결**됨 (기존 계정 로그인·병합 경로는 불인정)
  3. **본인 프로필 티저 생성 완료**
- 상한: 초대자당 하루 3장, 누적 10장 (함수 상수 → 설정값으로 옮길 수 있음)
- 피초대자 혜택(선택): 템플릿 블록 1개 추가 공개 (추가 비용 0원)

### 8.2 방어 계층

| 계층 | 장치 | 비고 |
|---|---|---|
| 1. 전환 조건 | 클릭·접속은 불인정, 신규 연결 + 본인 티저 완료만 인정 | 기존 회원끼리 맞초대 불가 |
| 2. 계정 신뢰 | 양측 카카오 계정 필수 | 계정 대량 생성 비용이 큼 |
| 3. 상한 | 일 3장 · 누적 10장, 초대자 행 잠금으로 동시성 처리 | |
| 4. 위험 신호 → 보류 | 같은 기기 지문의 신규 연결 다수, 짧은 시간 연속 가입 등 → `HELD` 후 검토 | **IP가 같다는 이유만으로 차단하지 않음** (같은 와이파이·통신사 NAT 오탐) |
| 5. 봇 차단 | 익명 로그인 Turnstile, API 레이트 리밋 | |

### 8.3 결정 필요
- 일일 상한 초과분: 거절(현재) vs 다음 날 지급(HELD 후 배치)
- 궁합 상대가 링크로 직접 정보를 입력하는 초대형 궁합 — 소유권·동의 모델이 필요 → Phase 2
